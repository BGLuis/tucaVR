# Network Protocol Test Environment (Phase 0.4 Sections 2/3)

Real servers (through Docker) for the protocols that `rust/protocols` implements,
used by the integration tests in `rust/protocols/tests/`. They exist to fill the gap
documented in `docs/phases/PHASE-0.1-MVP.md` (T6.1/T6.3/T7.1: "never tested
against a real server") and to extend the integration tests to DASH and WebDAV.

Do not use them manually — run `./scripts/test-network-protocols.sh` from the repo
root, which generates the fixtures, brings the containers up, runs the Rust tests
and tears everything down.

## Services

| Service | Protocol | Host port | Credentials |
|---|---|---|---|
| `smb-test` | SMB2/3 (`dperson/samba`) | 14450 (mapped from 445) | `authshare`: user `vruser` / password `vrpass123`. `guestshare`: no authentication. |
| `http-test` | Plain HTTP (nginx) | 18080 | — |
| `https-test` | HTTPS with a self-signed TLS certificate (nginx) | 18443 | Certificate generated at runtime, see below |
| `ftp-test` | FTP (`delfer/alpine-ftp-server`, vsftpd) | 12121 (mapped from 21) + 12100-12110 (passive) | user `vruser` / password `vrpass123`, home `/ftp/vruser` |
| `sftp-test` | SFTP (`atmoz/sftp`, OpenSSH) | 12222 (mapped from 22) | user `vruser` / password `vrpass123` **or** key `ssh-keys/vrplayer_test_key` (both work at the same time), home `/home/vruser`, fixture in `fixtures/` inside the home |
| `webdav-test` | WebDAV (`bytemark/webdav`, Apache + mod_dav_fs) | 18099 | user `vruser` / password `vrpass123` (Basic), data in `fixtures/webdav/` (its own directory, not shared with the other services) |
| `nfs-test` | NFSv3 (NFS-Ganesha in user space + `rpcbind`) | 111 (rpcbind), 2049 (NFS), 20048 (MOUNT) | No authentication (AUTH_UNIX uid 0), read-only export `/export` = `fixtures/`. MOUNT sits on 20048, **not** on 2049 — as on a `nfs-kernel-server` — and only rpcbind says which one |
| — (DASH) | MPD served by `http-test` itself | 18080 | No authentication — `fixtures/dash/template/manifest.mpd` (SegmentTemplate) and `fixtures/dash/singlefile/manifest.mpd` (SegmentBase), generated by ffmpeg on every run |

All of them serve the contents of `fixtures/` (generated by the setup script — a
random binary file, `testfile.bin`, with its `sha256` saved next to it).

The `smb-test`, `sftp-test` and `webdav-test` images are pulled as `:latest`
(unpinned), and `ftp-test` has no tag at all; `http-test`/`https-test` use
`nginx:1.27-alpine`. Pin them if a test starts failing after an upstream image
update. The SFTP key under `ssh-keys/` is a disposable test key committed on
purpose (see below); secret scanners may flag it.

## Folder-Scan Fixtures and Pool Tests

The script also generates `fixtures/scan/` (`empty-a/nested`, `empty-b`, `empty-c` with only
`.txt` files, and `with-media` with a `clip.mp4` placeholder). The fixtures root cannot be used for
"no media" scans because it also holds `dash/`. The SMB and SFTP session-pool tests count
authentications and simulate dropped links through a small TCP proxy in
`rust/protocols/tests/common/mod.rs` (one accepted connection = one authentication) instead of
parsing container logs.

## HTTPS Certificate

`https-test` generates a self-signed certificate (`CN=localhost`) the first time it
comes up, through `entrypoint.sh` running inside the nginx image's official
`/docker-entrypoint.d/` hook — not at image build time, because the volume mounted at
`/etc/nginx/tls` would hide anything generated at build time. The public certificate
lives in `https-test/certs/cert.pem` (on the host, through a bind mount) and is passed
to the Rust tests as `VRPLAYER_TEST_CA_CERT`, used by `protocols::http::base_client()`
**only** when the `integration-tests` cargo feature is enabled (never in production —
see `rust/protocols/src/http.rs`).

## Manual Validation Performed

Before writing the automated tests, each service was tested manually (`smbclient`,
`curl --cacert`, and for FTP an ad-hoc Rust client through `suppaftp`) to confirm
that the `dperson/samba` syntax, nginx's TLS/range-request config and
`delfer/alpine-ftp-server`'s passive mode were correct — all four matched the
original file's sha256 through a full read (FTP also through partial range reads
simulating the MKV cue seeks, see `rust/protocols/tests/ftp_integration.rs`).

For `sftp-test`: validated manually with the system's real `ssh`/`sftp` clients —
`ssh -i ssh-keys/vrplayer_test_key -p 12222 vruser@127.0.0.1 -s sftp` (key
authentication, no password) and an interactive `sftp` session listing `fixtures/`
and reading `testfile.bin` — before running the Rust suite
(`rust/protocols/tests/sftp_integration.rs`, 7 tests including two dedicated to key
authentication), which also matched the sha256 through a full read, small blocks
forcing multiple real seeks on the SFTP handle, and a jump backwards after a
sequential read.

## Gotcha: FTP Passive Mode Inside Docker

As the phase doc (`PHASE-0.2-3D-NETWORK.md`, section 6) warns, active mode never
works behind NAT — but passive mode *inside Docker* has its own trap: the FTP server,
when answering a `PASV`, announces the IP address at which the client must open the
data connection. By default `vsftpd` would announce the container's internal IP
(something like `172.17.0.x`), which the client running on the host cannot reach —
the data connection hangs/expires even though the control port works perfectly.
Solved by fixing `ADDRESS=127.0.0.1` in `ftp-test`'s envs: since this project's tests
*always* run on the same host as Docker (never from another machine), announcing
`127.0.0.1` works — Docker's `docker-proxy` forwards the mapped passive ports
(`MIN_PORT`/`MAX_PORT` = 12100-12110) back to the same `127.0.0.1` the client already
uses for the control port. If this ever needs to run against a remote Docker (CI on
another machine, for example), `ADDRESS` would have to become the IP really reachable
by the client, no longer `127.0.0.1`.

## Gotcha: chroot and the `atmoz/sftp` Public Key

Two permission traps specific to this image (a real OpenSSH, which is much stricter
than `vsftpd`/`smbd` about this):

1. **A chroot requires root ownership of the home.** OpenSSH refuses
   `ChrootDirectory` (`atmoz/sftp` uses `%h`, i.e. `/home/vruser`) if that
   directory — or any of its parents — is not owned by `root:root` and not writable
   by group/others ("bad ownership or modes for chroot directory", the connection
   silently drops on the client side). The image's entrypoint already does
   `chown root:root`/`chmod 755` on `/home/vruser` on every start, so the fixture
   **cannot** be mounted over the home itself — only a subdirectory inside it. That
   is why `docker-compose.yml` mounts `./fixtures:/home/vruser/fixtures:ro` (not
   `:/home/vruser:ro`), and the Rust tests list/open files inside `fixtures/...`, not
   at the root — unlike SMB/FTP, where the fixture *is* the root.
2. **Public key convention:** `atmoz/sftp` does not read `authorized_keys` directly
   from a mount — it concatenates any file inside `~user/.ssh/keys/` into a new
   `authorized_keys` on every start (the image's own `create-sftp-user` script), with
   the correct `chown`/`chmod 600` automatically. That is why the mount is
   `./ssh-keys/vrplayer_test_key.pub:/home/vruser/.ssh/keys/vrplayer_test_key.pub:ro`
   (the file name inside `keys/` does not matter). The test key
   (`ssh-keys/vrplayer_test_key{,.pub}`, ed25519, no password) is disposable,
   generated only for this environment — never reuse a real key here.

## `nfs-test` Gotchas

- **Host ports 111/2049/20048 must be free.** The client talks to rpcbind on the fixed
  port 111 (it cannot be configured), so it cannot be remapped. If your host runs an
  `rpcbind` or an NFS server, stop it first.
- **`netbase` in the image.** Without `/etc/services` (the Debian *slim* image) `rpcbind`
  cannot resolve the `sunrpc` service, opens only the local socket and port 111 never
  listens: Docker accepts the connection on the proxy and resets it
  (`Connection reset by peer`).
- **`rpcinfo -p` vs `rpcinfo`.** `-p` shows the portmap v2 dump (what the client uses
  through `GETPORT`); without `-p` it shows the v3/v4 registrations per netid.
- **Registration only at start-up.** Ganesha registers NFS and MOUNT with rpcbind when it
  starts; `entrypoint.sh` waits for rpcbind to answer first. If you restart only rpcbind,
  restart the whole container.
- **`allow_set_io_flusher_fail`** and the compose `cap_add`/`seccomp:unconfined` keep
  Ganesha from aborting with `PR_SET_IO_FLUSHER ... EPERM` on Docker without full
  privileges.

## Troubleshooting

**`Permission denied` when deleting `https-test/certs/`**: the certificate is
generated *inside* the container as root, so the file on the host is also owned by
root. A plain `rm -rf` from your user fails. Use:

```text
docker run --rm -v "$(pwd)/https-test/certs:/certs" alpine sh -c "rm -rf /certs/*"
```

That is only needed if you want to force the certificate to regenerate (e.g. the
X.509 extensions changed) — the normal script reuses the existing certificate
between runs.

**`invalid peer certificate: Other(OtherError(CaUsedAsEndEntity))`** coming from
`rustls`: the certificate was generated without an explicit `basicConstraints=CA:FALSE`.
Alpine's OpenSSL, by default, marks self-signed `-x509` certificates as `CA:TRUE` —
`curl`/OpenSSL accept that when verifying, but `rustls` (used by `reqwest` in
`protocols::http`) rejects it as a leaf/end-entity cert. Fixed in `entrypoint.sh`
with `-addext "basicConstraints=critical,CA:FALSE"` — if you edit the certificate
generation, do not remove that extension.

## Gotcha: the DASH `SegmentBase` Manifest Is Hand-Written, Not Generated by ffmpeg

`rust/protocols/src/dash` only understands `SegmentBase` with an `<Initialization range="...">`
child (a single media segment = the whole file after the init) — **not** `SegmentList`
(multiple explicit `<SegmentURL>`s), which is what `ffmpeg -f dash -single_file 1`
actually produces. Instead of depending on the exact XML a specific ffmpeg version
generates for `SegmentList` (fragile across versions), `scripts/test-network-protocols.sh`
concatenates the video init segment (`template/init-0.m4s`) with all the video chunks
already generated for the `SegmentTemplate` manifest (`template/chunk-0-*.m4s`) into a
single valid continuous fMP4 file (`singlefile/video.mp4` — init + moof/mdat
concatenated is exactly what a single-file `SegmentBase` contains) and writes
`singlefile/manifest.mpd` by hand, with the `Initialization` byte range computed from
the real init segment size (`stat -c%s`). That guarantees a syntactically correct
`SegmentBase` MPD regardless of the installed ffmpeg version, exercising the real
production code against a genuine media file.

## `dperson/samba` Share Syntax

Field order in `-s`: `name;path;browsable;readonly;guest;users;admins;writelist;comment`.
Easy to get wrong (the order `readonly` before `guest` is not obvious) — if you touch
`docker-compose.yml`, validate again with `docker run --rm dperson/samba -h`.
