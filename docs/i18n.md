# Internationalization (i18n)

> Context: this document covers T8.1–T8.5 of `docs/phases/PHASE-0.1-MVP.md`
> (section 8) and T10.1–T10.5 of `docs/phases/PHASE-0.3-POLISH-AUDIO.md` (section 10).
> It records what was implemented, the naming convention adopted, the
> architectural decision (T8.4), the neutral Spanish (ES) support, and the
> automated parity rules enforced by a JVM unit test. See also REQUIREMENTS.md,
> section 3.7 (RF-I18N-001..005).

## 1. State Before This Round

There was no `app/src/main/res/` in the project. The app's entire UI is built
from programmatic Android Views (`TextView`/`EditText`/`Button`/`SeekBar`
constructed in Kotlin, not XML layouts) inside `Presentation` classes
(`android.app.Presentation` on a `VirtualDisplay`, projected as textures onto
3D quads by C++ — see `native/src/vr_player_app_vulkan.cpp`). The one exception
is the in-app web browser panel (`browser/`), which uses Jetpack Compose. Every
user-visible text was hardcoded as string literals in Kotlin, mainly in
`VRPresentation.kt` (the Home -> Local files / Network -> Player flow) and
`VRControlsPresentation.kt` (the play/pause/seek/volume/speed panel).

## 2. What Was Done

- `app/src/main/res/values/strings.xml` — **English**, the Android default/
  fallback resource (T8.1). Used whenever there is no more specific
  `values-XX` folder for the system locale.
- `app/src/main/res/values-pt-rBR/strings.xml` — **Portuguese (BR)** (T8.2),
  the same language the UI was originally written in. The keys and their
  order mirror the default file exactly, to make side-by-side diffing and
  review easier.
- `app/src/main/res/values-es/strings.xml` — **neutral Spanish (es)** (T10.1 &
  T10.2 of Phase 0.3), covering every Spanish-speaking locale as a fallback.
  The keys, order and positional placeholders strictly mirror the default file.
- Every user-visible literal in the UI classes was replaced by
  `context.getString(R.string.xxx)` / `context.getString(R.string.xxx, arg1,
  arg2)`. Today these live in `VRPresentation.kt`, `VRControlsPresentation.kt`,
  `VRModalPresentation.kt`, the screens under `screens/` (`HomeScreen`,
  `NetworkSmbScreen`, `SettingsScreen`, `PlayerScreen`, ...) and the components
  under `designsystem/` (for example the "Back" button of `VoidPanelChrome.kt`,
  shared by every screen). `AndroidManifest.xml` also references
  `@string/app_name` instead of hardcoding the app name. `VRActivity.kt` also
  uses `R.string` resources (Toasts and dialogs).
- Files scanned and found to have **no** UI strings to externalize (confirmed
  by grep, not assumed): the pure-logic layer under `filebrowser/*.kt` (no text
  — the screens draw it), `network/SmbCredentialStore.kt` and
  `UrlHistoryStore.kt` (only internal `SharedPreferences`/JSON keys, not UI
  text), and the `designsystem/` components that carry no fixed text of their
  own.
- Native `<plurals>` resources are used for quantity-dependent strings
  (`browser_results_count_format`, `browser_folder_summary_format`, and
  `playlists_item_count`). These support distinct singular and plural grammatical
  forms via `context.resources.getQuantityString(...)`.
- Strings with interpolation became `getString(R.string.xxx, arg1, arg2, ...)`
  with positional placeholders (`%1$s`, `%1$d`, `%1$.2f`) instead of Kotlin
  concatenation, specifically to allow reordering arguments in another language
  (T8.5 / an explicit caution of the phase doc). A concrete example:
  `"${server.name}/${source.path}"` in the player screen became
  `getString(R.string.player_label_smb_source_format, source.server.name, source.path)`
  with `player_label_smb_source_format = "%1$s/%2$s"`.

### What Was **Not** Externalized, On Purpose

Not every string literal in Kotlin is a translatable UI string. These were left
as they are (a conscious decision, not an oversight):

- Internal protocols/formats: the `"ERROR:"` prefix returned by Rust through
  JNI, the `"\t"`/`"\n"` delimiters of SMB listings, URI schemes (`"http://"`,
  `"https://"`), `SharedPreferences`/JSON keys. These are contracts between
  layers, not screen text.
- Pure path concatenations with no natural-language content, e.g.
  `"${server.share}/$networkBrowsePath"` (the SMB navigation subtitle) and
  `"$requestedPath/$name"` (path assembly when entering a subfolder). A path
  separator `/` does not change between languages; there is no real gain in
  turning that into a `%1$s/%2$s` resource just for the sake of it.
- Symbols/emojis with no letters (`"<<"`, `">>"`, `"✕"`, `"🎵"`) — they carry
  no linguistic content to translate. Emojis used as a prefix of a label WITH
  text (e.g. `"📁  Local files"`) stay inside the translatable string (they are
  part of the resource); only those that are the entire button by themselves
  were left out.
- `String.format("%02d:%02d", ...)` in `VRControlsPresentation.formatTime` — a
  numeric MM:SS format, not language text.
- Purely numeric/technical example hints with no letters (`"192.168.1.10"`,
  `"445"`) — there is nothing to translate in a sample port number or IP.

## 3. Naming Convention (T8.3)

`screen_element_action`, e.g.: `player_btn_play_pause`,
`browser_label_size_mb_format`, `network_smb_form_status_connecting`.

- **`screen`**: the prefix of the screen/flow — `home`, `browser` (local
  files), `network` (the Network tab, including the sub-flows
  `network_url_*`/`network_smb_*`/`network_files_*`), `player` (the
  post-media-selection screen + the controls panel, which share the same
  `player_` prefix because they are the same "screen" from the user's point of
  view).
- **`common_`**: a pseudo-"screen" for elements reused in more than one place —
  today: the "Back" button of `VoidPanelChrome` (shared by every screen with a
  header), and the `📁 %1$s`/`🎬 %1$s` row formats used both by the local
  browser (`FileAdapter`) and by SMB directory navigation. Rule: if the SAME
  string (not just a similar one) is used by more than one screen, it becomes
  `common_`; otherwise it stays under the specific screen's prefix, even if the
  content is similar (e.g. `network_files_loading` != any other "loading" in the
  app today — there is no generic `common_loading` yet because only one place
  uses it).
- **`element`**: the element type — `btn` (button), `label`/`title` (static
  text), `hint` (field placeholder), `status` (dynamic status message), `row`
  (list row).
- **`action`/free suffix**: what the element does or represents, e.g.
  `play_pause`, `add_server`, `host_required`. The **`_format`** suffix is
  reserved specifically for strings with positional placeholders (`%1$s`,
  `%1$d`, `%1$.2f`) used through `getString(res, arg...)` — it signals to
  whoever is translating that the string has arguments and their order may
  change.
- Plurals (`<plurals>`) follow the same naming scheme, with no special suffix
  beyond what already describes the content (`network_smb_form_status_connected`)
  — the fact that it is `<plurals>` instead of `<string>` is already visible in
  the XML/usage (`resources.getQuantityString(...)`), and does not need to be
  repeated in the name.

## 4. T8.4 — Strings in the C++ Layer: an Architectural Finding

Task T8.4 of the phase doc originally assumed "Strings in the C++ layer
(OpenXR UI): use numeric IDs mapped to strings loaded from Kotlin via JNI", and
the warning in section 8 reinforced it: "The controls UI is rendered in
C++/OpenXR, but the translation strings are in Android resources (Kotlin). Pass
the translated strings from Kotlin -> C++ at initialization or via callback."

**That does not match this project's real architecture**, verified directly in
`native/src/*.cpp` (a complete grep, not just a spot read): there is no UI text
rendered by C++. All the text the user sees (Home, file browser, network/SMB
forms, the controls panel) is drawn by native Android Views
(`TextView`/`EditText`/`Button`/`SeekBar`) inside the Kotlin `Presentation`
classes, which are rendered to a `VirtualDisplay` and only AFTER that captured
as a texture projected onto a 3D quad by C++. C++ only does raycasting against
the quad geometry and composition/blending of the resulting textures; it never
queues, draws or even knows about individual glyphs/strings. There is none
today, and no architectural plan for there to be, an "OpenXR UI" that draws
text directly — that T8.4 premise described a different architecture from the
one this project has (closer to, for example, a direct SDF text renderer in
OpenGL/Vulkan, floated as a note in T4 but not implemented).

**Decision**: T8.4 is marked as complete with this note, instead of
implementing a JNI string bridge (Kotlin -> numeric IDs -> C++) that would have
no real consumer — there is no code in `native/` that would need to receive or
use those strings. Building that bridge "because the doc asks for it" would be
dead scaffolding (the same pattern already identified and avoided in T1.7 for
UniFFI). `docs/phases/PHASE-0.1-MVP.md` T8.4 has since been reworded to state
this strategy directly. If a native C++/OpenXR UI screen ever comes to exist in
the future (outside the scope of v0.1, with no indication it will be needed
since the current "Presentation renders, C++ only displays the texture" pattern
covers everything so far), the strategy recommended at that point would be to
reuse the SAME `res/values*/strings.xml` from Kotlin, exposing the resolved
strings through JNI (Kotlin calls `context.getString(...)` and passes the result
to C++ through an `extern "C"` function) — never duplicating the strings inside
C++. That recommendation formalizes the "do NOT duplicate strings in C++"
warning of the doc even though there is, today, no C++ that needs them.

## 5. How to Add a New Language (T8.5)

1. Pick the correct BCP-47/Android qualifier for the target locale. The format
   is `values-<lang>` (e.g. `values-es` for neutral Spanish, implemented in
   Phase 0.3 Section 10) or `values-<lang>-r<REGION>` for a regional variant
   (e.g. `values-pt-rBR`, already existing; `values-es-rES` if you need to
   distinguish Spain's Spanish from Latin American Spanish).
2. Create `app/src/main/res/values-<qualifier>/strings.xml` by copying the
   STRUCTURE (keys, order, section comments) of
   `app/src/main/res/values/strings.xml` — not of `values-pt-rBR`, so as not to
   accidentally inherit English already translated into Portuguese.
3. Translate EVERY `<string>`/`<plurals>` while keeping:
   - The positional placeholders in the same count and type (`%1$s` stays
     `%1$s`, it does not become `%1$d`), possibly changing the ORDER
     (`%2$s ... %1$s`) if the language calls for it.
   - `<plurals>`: Portuguese, English and Spanish only have `one`/`other`; other
     languages (Russian, Arabic, Polish, etc.) have additional categories
     (`few`, `many`, `zero`) — the [official Android plurals
     documentation](https://developer.android.com/guide/topics/resources/string-resource#Plurals)
     and the [CLDR table](https://cldr.unicode.org/index/cldr-spec/plural-rules)
     list the rules per language. Do not assume `one`/`other` suffice for every
     new language.
   - The prefix emojis/symbols (e.g. `📁`, `🌐`, `⚠`) stay — they are not text
     to translate, they are part of the label's "icon".
4. Do **not** create a new key without adding it to ALL the files:
   `values/strings.xml`, `values-pt-rBR/strings.xml` and `values-es/strings.xml`
   simultaneously (parity must be 100%). If a key exists in only one language,
   Android uses the `values/` (default) fallback for those that lack the key —
   it works, but silently breaks parity between languages.

   **Automated parity guard (`I18nParityTest.kt`)**: the project has a mandatory
   JVM unit test at `app/src/test/java/com/tucavr/I18nParityTest.kt` that runs
   in `./gradlew testDebugUnitTest` and in CI, failing if:
   - There is any key discrepancy between `values/strings.xml` and any
     dynamically discovered `values-*/strings.xml` directory.
   - The key declaration order is not strictly identical.
   - Any translated string omits or alters positional placeholders (`%1$s`,
     `%1$d`).
   - Any string uses non-positional placeholders (`%s` or `%d` without `$`),
     preventing formatting breakage and runtime exceptions.
   - The `<plurals>` elements lack the required forms (`one` and `other`).
   - Singular (1) and plural (2) resource formatting produces unexpected
     placeholders or malformed output.
5. Follow the naming convention of section 3 for any new key (the same
   `screen_element_action` prefix, `common_` for reused elements, `_format` for
   strings with positional arguments).
6. **Where NOT to duplicate strings**: there is only ONE real place for UI text
   today — `app/src/main/res/values*/strings.xml`, consumed by Kotlin through
   `context.getString(...)`. There are no duplicated strings in C++ (see
   section 4) — a conscious decision, not a real problem to avoid today, but
   documented here because the phase doc itself explicitly asks "do NOT
   duplicate strings in C++" and that recommendation still holds if/when C++
   comes to need its own text in the future.
7. No Kotlin code change is needed just to add a language — the Android
   resource system switches the active `Locale`/`Configuration` automatically
   based on the system language configured on the headset/device, with no
   custom locale-detection code in this project. This is standard platform
   behavior.

### 5.1 Unicode CLDR Plural Categories and Language Rules

Android's `<plurals>` implementation relies on the Unicode Common Locale Data
Repository (CLDR) plural rules. In CLDR, grammatical number is partitioned into
up to 6 symbolic categories:

| Category | Description | Examples |
| --- | --- | --- |
| `zero` | Specifically for 0 in languages that grammatically treat 0 uniquely. | Arabic (0), Latvian (0) |
| `one` | Singular form. | English ($n=1$), Spanish ($n=1$), Portuguese ($n=1$) |
| `two` | Dual form (exactly two). | Arabic (2), Hebrew (2), Welsh (2) |
| `few` | Paucal form (small quantities). | Russian ($n \pmod{10} \in [2,4]$ and $n \pmod{100} \notin [12,14]$), Polish |
| `many` | Genitive / large quantity form. | Russian ($n \pmod{10} = 0$ or $\in [5,9]$ or $n \pmod{100} \in [11,14]$), Arabic (11–99) |
| `other` | General plural form / fallback. | Mandatory in every locale for counts not matched by other categories. |

#### Rules for Currently Supported Locales

- **English (`en`, default `values/`)**: Supports `one` ($n=1$) and `other` (all
  other numbers, including 0: *"0 items"*).
- **Portuguese (Brazilian, `values-pt-rBR/`)**: Supports `one` ($n=1$) and `other`
  (all other numbers: *"0 itens"*).
- **Spanish (`values-es/`)**: Supports `one` ($n=1$) and `other` (all other
  numbers: *"0 elementos"*).

When contributing translations for languages with complex plural rules (such as
Russian, Arabic, Czech, or Polish), contributors must consult the [Unicode CLDR
Plural Rules table](https://cldr.unicode.org/index/cldr-spec/plural-rules) and
provide all applicable plural items in the `<plurals>` tag.

## 6. Validation and Known Limitations

- `./gradlew :app:compileDebugKotlin` and `./gradlew :app:testDebugUnitTest`
  pass with the externalized strings and with the `I18nParityTest` guard
  validating the 3 locales (English, Brazilian Portuguese and Spanish).
- **Not validated on a real Quest 3 headset** (no hardware access when this was
  written, the same caveat as other sections of the phase doc): the automatic
  language switch through the Android system's `Configuration`/`Locale` is a
  standard platform mechanism that has existed for decades, not a customized
  behavior of this app — but the exact behavior inside a `Presentation` on a
  `VirtualDisplay` (the same pattern already raised as an uncertainty for the
  virtual keyboard in T6.4/T7.3) was never visually confirmed on a physical
  Quest 3. The risk is considered low (it is the most basic and tested resource
  resolution mechanism of Android, not something exotic like an IME on a
  VirtualDisplay), but it is recorded as not verified, not as validated.
- `I18nParityTest` guarantees at the JVM level that all the keys, orders and
  placeholders are perfectly synchronized between the 3 languages.
